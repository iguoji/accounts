# 代理池

代理池用于收集代理 IP，检测代理支持的协议及当前可用性，并通过内网 HTTP API 向其他服务提供可用代理。

当前版本为 v0.1.4。当前已经实现兜底源头同步、按源头变化规律动态调度、全局串行采集、HTTP、HTTPS、SOCKS4、SOCKS5 四协议测活、Redis 状态维护、按业务域名过滤受限出口 IP、业务封禁反馈，以及可用代理查询和运行统计接口。

## 思路逻辑

> 本章节描述整个代理池在用户脑海中的目标形态，由用户维护。Agent 不得自行新增、删除、改变含义，或根据现有代码反推用户意图。

- 采集池
    - `source.yaml` 作为系统定期采集的兜底数据源。
    - 探测源头实际更新时间，后续依此进行定期采集。
    - 串行探测和采集，避免出现 429、403 等风控。
    - 解析代理地址中的账号、密码、IP 及端口等必要信息。
    - 过滤格式错误、非法地址和非公网地址，最终去重后入库。
- 检测池
    - 周期性异步分块批量测活库中的 IP，检测 HTTP、HTTPS、SOCKS4、SOCKS5 四种协议。
    - 根据测活结果维护数据库中的 IP 状态。
- 接口层
    - 提供对内网的 HTTP API，包含全部可用代理、随机可用代理、统计、反馈和导入等能力。
    - 全部代理：返回全部可用代理。
    - 随机代理：返回随机可用代理。
    - 统计：返回各项监控指标数据。
    - 反馈：标记指定代理无法用于某类业务。
    - 导入：导入一批第三方代理 IP。

## 固定规则

> 本章节记录用户已经确定、后续设计与开发必须遵守的规则，由用户维护。Agent 发现规则存在歧义、冲突、缺失或无法实施时，应说明问题并提出建议。只有用户明确同意后，Agent 才能代为整理，且不得改变原意。

- 每个代理均需要检测 HTTP、HTTPS、SOCKS4、SOCKS5 四种协议。
- 地址合法性必须使用规则判断。只有公网单播地址可以入库，内网、私有、回环、链路本地、保留、组播和广播地址必须拒绝。
- 日志只记录系统运行信息，不记录每个代理的测活结果明细。

## 功能模块

本章节描述当前代码已经实现的行为。思路逻辑中尚未实现的反馈和导入不会在这里写成已有能力。

### 采集

服务启动时读取 `source.yaml`，将其中的兜底源头同步到 Redis。每个源头拥有独立状态、调度时间和检查记录。采集循环每次只处理一个到期源头，完整处理并重新入队后才会处理下一个源头，因此所有源头探测和采集在全局范围内串行执行。

一轮采集的生命周期如下：

```text
读取 source.yaml 并同步兜底源头
    ↓
从 source_probe_queue 取出一个到期源头
    ↓
使用 ETag 或 Last-Modified 发起条件请求
    ↓
比较原始内容摘要和有效代理集合摘要
    ↓
仅在有效代理集合变化时增量写入 Redis
    ↓
根据历史变化间隔、连续未变化次数或失败次数安排下次检查
```

当前采集模块具有以下行为：

- `source.yaml` 只负责提供兜底源头。源头首次发现后，其后续状态和调度信息由 Redis 保存。
- 源头 URL 经过规范化后计算 SHA-256 摘要，作为稳定的 `source_id`。
- 请求会携带上次保存的 `ETag` 或 `Last-Modified`。远端返回 304 时，直接视为内容未变化。
- 成功响应会同时计算原始响应内容摘要 `content_hash`，以及解析、过滤、去重后的有效代理集合摘要 `proxy_set_hash`。
- 原始内容未变化时，不更新代理；原始内容变化但有效代理集合未变化时，只更新源头记录；只有有效代理集合变化时，才增量写入代理。
- 首次成功采集没有历史摘要，因此会作为一次变化处理。
- 成功响应没有解析出任何有效代理时按异常处理，不用空集合覆盖已有摘要。
- 同一 IP 和端口具有不同认证信息时，视为不同代理。
- 已存在且未软删除的代理不会重复创建，也不会因为再次采集而刷新状态。
- 已软删除的代理再次采集到时，只有软删除时间达到 `PROXIES_DEAD_REVIVE_AFTER` 后才会复活；复活后重置为待检测状态并重新加入测活队列，不会直接恢复为可用。
- 有实际内容变化记录时，使用最近十次变化间隔的中位数推测下次检查时间；历史不足时使用默认间隔；连续未变化和连续失败会逐步延长检查间隔。
- 403 或 429 会触发同一站点的全局冷却。同站点其他源头在冷却结束前不会发送请求。
- 请求失败与内容未变化分别记录。单个源头失败不会使采集循环退出，长期失败只保留异常状态，不自动删除源头。
- 当前实现使用 `response.text()` 读取单个源头的完整响应，再进行摘要和解析，因此单个超大源文件会占用与响应体大小相近的内存。
- 源头从调度队列取出后发生异常时会延迟重新入队；服务启动时还会扫描源头索引，恢复异常退出造成的漏失调度。

### 测活

新代理入库后会立即进入 `check_queue`。调度循环从中原子取出已经到期的代理，在并发上限内执行测活。

每个代理的生命周期如下：

```text
进入测活队列
    ↓
到期后取出
    ↓
并发检测四种协议
    ↓
更新代理状态和可用协议索引
    ↓
可用代理按固定间隔复查
    ↓
失败代理按连续失败次数延后复查
    ↓
达到失败上限后进入软删池
```

四种协议会并发检测。每种协议通过代理访问主测活渠道，返回 HTTP 200 且响应正文中含有 IP 时判定成功。只有主渠道明确返回 404 时才尝试备用渠道；超时、连接错误或其他非 200 状态直接判定该协议失败。

任一协议成功时，代理整体状态为可用，连续失败次数归零。四种协议全部失败时，连续失败次数增加，并按配置计算下次检测时间。连续失败次数达到 `PROXIES_MAX_CONSECUTIVE_FAIL` 后，代理进入软删池。

服务启动时会校准统计数据和测活队列。异常退出期间已经从队列取出但尚未放回的非死亡代理会重新入队，死亡代理遗留的队列成员会被清理。

### 内网接口

查询接口接受 GET 请求，业务反馈接口接受 POST 请求。

#### 获取可用代理列表

- 地址：`/proxies`
- 参数：
    - `protocols`：可选。为空时查询所有协议；可以重复传入，也可以使用逗号分隔。
    - `page`：可选，默认为 1。
    - `count`：可选，默认为 20。
    - `domain`：可选。传入域名或网址后，排除该域名下仍处于封禁期的所有同 IP 代理。
- 返回：JSON 数组 `[{ip, port, protocols, username?, password?}]`。

多种协议采用并集语义。列表在 Redis 内完成候选集合合并、排序、分页和结果组装，一次请求只往返 Redis 一次。

#### 随机获取一个可用代理

- 地址：`/proxy`
- 参数：
    - `protocols`：可选，规则与 `/proxies` 相同。
    - `domain`：可选，规则与 `/proxies` 相同。
- 返回：一个代理的 JSON 对象；没有符合条件的代理时返回空对象 `{}`。

随机选择以符合协议条件的唯一代理集合为范围。

#### 反馈某个代理无法访问指定网站

- 地址：`/feedback`
- 方法：`POST`
- 请求体：`{ip, port, domain, blocked_seconds, reason?}`。
- `blocked_seconds` 是调用方决定的封禁秒数。代理池信任内部子系统的判断，不解析 HTTP 状态码或验证码内容。
- `reason` 可选，最多 1000 个字符，只用于日志记录，不参与判断。
- `ip` 和 `port` 用于确认反馈对应池中已有代理；真正的业务封禁范围按规范化后的 `domain + IP` 保存，不区分端口、协议、账号或密码。
- 相同 IP 和域名的重复反馈只能延长封禁时间，不能缩短现有封禁。

#### 获取运行状态

- 地址：`/stats`
- 参数：无。
- 返回：代理总数、可用数、未检测数、冷却数、软删数、正在测活数，以及最近采集和测活时间与累计次数。

统计满足：

```text
proxy_total = proxy_available + proxy_unchecked + proxy_cooldown
```

`proxy_dead` 单独计数。`proxy_checking` 是运行时正在测活的数量，可能与数据库状态分段重叠。

测活任务同时具备请求级超时和任务级硬超时。任务级硬超时会沿完整调用链主动取消尚未结束的网络请求，待请求与代理连接清理完成后才释放并发槽位；已取消的任务不会继续写入 Redis，避免后台残留请求造成实际并发失控或旧结果覆盖新结果。

导入接口属于思路逻辑中的规划，当前尚未实现。

## 数据结构

本服务使用 Redis 保存运行数据。

### 代理状态 `proxy:{代理标识}`（Hash）

每个代理保存一份状态记录。IPv6 在代理标识中使用 `[IP]:端口` 形式；认证信息经过百分号编码，避免冒号等字符造成歧义。

|字段|描述|
|---|---|
|`ip`|代理 IP，避免从标识反向拆分|
|`port`|代理端口|
|`username`|可选的认证用户名|
|`password`|可选的认证密码|
|`status`|0 表示当前不可用，1 表示当前可用|
|`consecutive_fail`|连续失败次数|
|`checked_at`|最后检测时间，毫秒时间戳；空字符串表示从未检测|
|`dead_at`|进入软删池的毫秒时间戳；复活后清空|

### 源头状态 `source:{source_id}`（Hash）

每个源头保存一份独立状态。`source_id` 是规范化源头 URL 的 SHA-256 摘要。

|字段|描述|
|---|---|
|`url`|规范化后的源头 URL|
|`enabled`|是否参与调度|
|`status`|最近一次处理结果|
|`content_hash`|最近一次有效响应的原始内容摘要|
|`proxy_set_hash`|最近一次有效代理集合摘要|
|`etag`|远端返回的 ETag|
|`last_modified`|远端返回的 Last-Modified|
|`last_checked_at`|最近一次实际请求时间，毫秒时间戳|
|`last_changed_at`|最近一次发现原始内容变化的时间|
|`next_check_at`|推测的下次检查时间|
|`consecutive_unchanged`|连续未变化次数|
|`consecutive_fail`|连续失败次数|
|`last_http_status`|最近一次请求的 HTTP 状态；网络错误为 0|
|`last_error`|最近一次错误信息|
|`change_intervals`|最近十次实际变化间隔|

### 源头索引 `source_ids`（Set）

保存所有已知 `source_id`，用于启动时遍历源头并修复漏失的调度记录。

### 源头调度队列 `source_probe_queue`（Sorted Set）

成员为 `source_id`，分值为下次检查的毫秒时间戳。调度器原子取出一个到期源头，处理完成后按新时间重新入队。

### 源头检查记录 `source_log:{source_id}`（Stream）

记录每次请求或冷却跳过的结果、HTTP 状态、两个摘要是否变化、有效代理数量、入库数量、耗时、下次检查时间、调度原因和错误信息。每个源头按 `PROXIES_SOURCE_LOG_MAX_LENGTH` 限制保留长度。

### 站点冷却 `source_site_cooldown:{hostname}`（String）

记录站点因 HTTP 403 或 429 进入冷却后的结束时间。同一主机名下的所有源头共用这段冷却时间。

### 测活调度队列 `check_queue`（Sorted Set）

|内容|描述|
|---|---|
|member|代理标识|
|score|下次允许检测的毫秒时间戳|

代理到期后通过 Lua 脚本原子完成“取出并移除”，测活完成后再根据结果重新加入队列，因此同一个代理不会被调度器重复取出。

### 可用协议索引 `available:{type}`（Set）

按照协议保存当前可用代理：

- `available:1`：HTTP
- `available:2`：HTTPS
- `available:3`：SOCKS4
- `available:4`：SOCKS5

集合成员为代理标识。每轮测活完成后，可用协议加入对应集合，失败协议从对应集合移除。

### 代理全集 `known_proxies`（Set）

保存所有已经采集入库的代理标识，用于判断代理是否已经存在。

### 软删池 `dead_pool`（Set）

保存连续失败达到上限的代理。再次采集到相同代理时，只有 `dead_at` 距今达到配置的等待时间，代理才会从软删池移出、重置状态并重新加入测活队列。历史数据缺少 `dead_at` 时，首次重新采集会补记当前时间，不会立即批量复活。

### 业务域名封禁 `domain_block:{规范化域名}`（Sorted Set）

成员为代理 IP，分值为封禁截止时间的毫秒时间戳。获取代理时如传入 `domain`，会排除分值仍晚于当前时间的 IP。由于网站通常按出口 IP 实施限制，同一 IP 下的所有端口、协议和认证组合都会一并排除。到期记录在查询时自动清理。

### 统计计数器 `stats`（Hash）

|字段|描述|
|---|---|
|`total`|未软删除的候选代理总数|
|`available`|当前至少有一种协议可用的代理数|
|`unchecked`|从未检测过的代理数|
|`cooldown`|已检测但当前不可用、正在等待复查的代理数|
|`dead`|已软删除的代理数|

满足 `total = available + unchecked + cooldown`，`dead` 单独计数。

服务启动时使用分批扫描校准这些计数，以修复异常退出或历史版本造成的统计偏差。`/stats` 请求本身不扫描代理全集。

### 元数据（String）

|键|描述|
|---|---|
|`meta:last_collect`|最近一次有效代理集合变化并完成入库的时间|
|`meta:collect_count`|有效代理集合变化并执行入库的累计次数|
|`meta:last_check`|最近一次测活完成时间|
|`meta:check_count`|累计测活次数|

## 运行维护

### 配置

配置统一从仓库根目录的 `../../.env` 读取，也可以通过同名进程环境变量覆盖。使用 Docker Compose 启动时，根目录的 `docker-compose.yaml` 会读取这些配置，并注入代理池和 Redis 容器。

代理池自身的配置项统一使用 `PROXIES_` 前缀，避免与其他子项目的配置重名。Redis 是多个子项目共同使用的基础服务，因此连接地址使用全局的 `REDIS_HOST` 和 `REDIS_PORT`，不归属于代理池前缀。

```ini
TZ                              = Asia/Shanghai  # 所有容器统一使用的时区

PROXIES_PORT                    = 3000  # HTTP API 端口
PROXIES_HOST                    = 0.0.0.0 # API 监听地址及 Docker 宿主机端口绑定地址

PROXIES_FETCH_TIMEOUT           = 30    # 单个数据源下载超时，单位秒
PROXIES_SOURCE_DEFAULT_INTERVAL = 3600  # 新源头或历史不足时的默认检查间隔，单位秒
PROXIES_SOURCE_MIN_INTERVAL     = 300   # 源头检查的最短间隔，单位秒
PROXIES_SOURCE_MAX_INTERVAL     = 86400 # 源头检查的最长间隔，单位秒
PROXIES_SOURCE_FAILURE_INTERVAL = 300   # 请求失败后的初始退避时间，单位秒
PROXIES_SOURCE_SITE_COOLDOWN    = 3600  # 站点触发 403/429 后的冷却时间，单位秒
PROXIES_SOURCE_LOG_MAX_LENGTH   = 100   # 每个源头保留的检查记录条数

PROXIES_INTERVAL                = 300   # 可用代理的复查间隔，单位秒
PROXIES_INTERVAL_BASE           = 2     # 连续失败时的指数退避基数
PROXIES_TIMEOUT                 = 5     # 单次测活请求超时，单位秒
PROXIES_RETRY                   = 3     # 单个协议的最多检测次数
PROXIES_MAX_CONSECUTIVE_FAIL    = 3     # 连续失败达到此次数后软删除
PROXIES_DEAD_REVIVE_AFTER       = 21600 # 软删除后再次采集到时允许复活的等待时间，单位秒
PROXIES_PROBE_CONCURRENCY       = 50    # 同时测活的代理数量上限

REDIS_HOST                      = redis  # 全系统共用的 Redis 地址
REDIS_PORT                      = 6379   # Redis 在 Compose 内部网络中的监听和连接端口
REDIS_PASSWORD                  = 请设置强密码 # Redis 服务和子系统连接使用同一密码

PROXIES_DEBUG                   = false
PROXIES_DEBUG_LOG_MAX_MB        = 20    # debug.log 单个文件最大容量，单位 MB
PROXIES_DEBUG_LOG_KEEP_FILES    = 3     # 轮转后保留的历史调试日志数量
PROXIES_DEBUG_SUMMARY_INTERVAL  = 60    # 测活状态汇总周期，单位秒
```

修改 `REDIS_PORT` 后，Redis 的内部监听端口和代理池连接端口会一起变化，不需要分别修改。使用 Docker Compose 时，`REDIS_HOST` 通常保持为服务名 `redis`。

Redis 不向宿主机发布端口，因此宿主机、局域网和外网都不能直接连接。代理池等 Compose 内部子系统通过 Compose 默认内部网络使用服务名 `redis` 连接，并使用同一密码认证。

`PROXIES_HOST` 当前同时用于控制代理池进程的监听地址和 Docker 在宿主机上的端口绑定地址。填写 `0.0.0.0` 表示允许从宿主机所有网络接口访问；如只允许本机访问，可填写 `127.0.0.1`。

### 日志

普通系统日志存放在 `../../logs/proxies/`，按 `yyyy-mm-dd.log` 命名。超过 30 天的日志会自动删除。

当 `PROXIES_DEBUG=true` 时，启动配置摘要、每次源头采集结果、调度异常和测活周期汇总会写入 `../../logs/proxies/debug.log`。正常的逐代理、逐协议请求和每秒空轮询不会逐条记录，避免百万级代理使日志快速膨胀。测活汇总默认每 60 秒记录一次，包括派发、完成、可用、失效、硬超时、并发峰值、耗时与协议成功数量。

调试日志达到 `PROXIES_DEBUG_LOG_MAX_MB` 后自动轮转，并按 `PROXIES_DEBUG_LOG_KEEP_FILES` 保留有限数量的历史文件。服务每次启动时仍会清空当前 `debug.log`，便于 Agent 从本次启动开始判断运行状态。日志不会输出代理认证密码。

日志只用于记录系统运行状态，不保存每个代理的测活结果明细。

### 启动恢复与异常处理

- 服务会等待 Redis 能正常响应命令后再启动业务。
- 启动时会校准代理统计和测活队列，并将启用但不在源头调度队列中的源头补回队列。
- 源头采集全局串行执行。每个源头处理完成后才会调度下一个源头。
- 单个源头请求失败会记录错误并按失败次数退避，不会停止后续源头采集。
- 成功响应没有有效代理时按异常处理，不覆盖已有源头摘要。
- 403 或 429 会使同站点源头进入共享冷却期，冷却期间的跳过行为也会写入源头检查记录。
- 源头在取出后遇到 Redis 等调度异常时会尝试重新入队；如果重新入队仍失败，则在下次服务启动时恢复。
- 单个代理或协议检测异常会转换为失败结果，不会使整个测活循环退出。
- 测活调度循环遇到 Redis 瞬时错误时会等待后重试。
- 收到 SIGINT 或 SIGTERM 时，服务会停止调度、关闭 HTTP 服务并断开 Redis。

### 常见问题

- 使用 `node-redis` 4.x 调用 `zAdd` 时，`NX`、`XX` 等写入条件属于独立选项，不能写入包含 `score` 和 `value` 的成员对象。项目中的源头队列初始化已按 `zAdd(key, member, options)` 的形式调用，避免 TypeScript 编译时报出 `NX does not exist in type ZMember`。
